# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Workout Timer — a Flutter Android app (single platform; iOS/web are not configured) for building and running interval workouts with TTS announcements. This is a fork of `blockbasti/just_another_workout_timer` (published on F-Droid and upstream GitHub Releases); the fork is published only via this repo's GitHub Releases under a different `applicationId` (`com.craeckie.workouttimer`) and therefore installs side-by-side with the upstream app — backups can be moved between them via export/import.

## Commands

Dev workflow uses [`script_runner`](https://pub.dev/packages/script_runner) (the `scr` command). Install once with `dart pub global activate script_runner`.

- `flutter pub get` — fetch dependencies
- `scr build` — runs the full codegen pipeline: `licenses`, `translations` (intl_utils), `launcher_icons`, `native_splash`, `build_runner`. Individual steps are also available (`scr translations`, `scr build_runner`, etc. — see `pubspec.yaml` `script_runner:` block).
- `flutter build apk` — build release APK (debug APK is what CI publishes)
- `flutter test` — run unit tests
- `flutter test test/utils_test.dart` — single file; append ` --plain-name "Utils.formatSeconds zero"` for one test
- `flutter analyze` — lint. `lib/layouts/oss_license_page.dart` needs `scr licenses` to generate `lib/oss_licenses.dart` first.

Codegen outputs (`lib/generated/**`, `lib/**/*.g.dart`, `lib/oss_licenses.dart`) are excluded from analyzer and should not be hand-edited — re-run `scr build` instead.

### `workout.g.dart` quirk

`lib/utils/workout.dart` declares `part '../workout.g.dart'`, so the committed generated file lives at `lib/workout.g.dart` — not next to its source. `build_runner`'s combining-builder writes to `lib/utils/workout.g.dart` (which gets ignored) and emits a `must be included as a part directive` warning every run, so the committed file does **not** auto-update after `scr build_runner`. When you add a `@JsonSerializable` class, copy the new functions from `.dart_tool/build/generated/just_another_workout_timer/lib/utils/workout.json_serializable.g.part` into `lib/workout.g.dart` by hand.

## Architecture

Three-layer split inside `lib/`:

- **`utils/workout.dart`** — pure data model (`Workout` → `Set` → `Exercise`, plus `Backup`). All JSON via `json_serializable` codegen (`workout.g.dart`). `Workout.fileVersion` drives migration; bump it when changing the schema and add a case to `Migrations._migrate`.
- **`utils/storage_helper.dart` + `utils/migrations.dart`** — file I/O. Workouts live as individual JSON files under `getExternalStorageDirectory()/workouts/`. `Migrations.runMigrations()` is called from `main()` on startup and mutates files in place. Filenames go through `Utils.removeSpecialChar` for safety.
- **`utils/history_helper.dart`** — completion-log I/O. Appends a `HistoryEntry` (title + timestamp) to a single `getExternalStorageDirectory()/history.json` file. Sibling of `workouts/`, deliberately outside it so `getAllWorkouts()` and backup export ignore it. The single write site is `Timetable.buildTimetable()`'s "workout complete" callback — partial runs are not recorded.
- **`layouts/`** — UI screens: `home_page` (list), `workout_builder` (edit), `workout_runner` (run), `history_page` (past completions, swipe-to-delete + clear-all), `settings_page`, `oss_license_page`. The runner delegates timing to `utils/timetable.dart`.

`Timetable` (`utils/timetable.dart`) is the timer engine: a `ChangeNotifier` that holds a `SplayTreeMap<int, Function>` of scheduled callbacks (TTS announcements, beeps, exercise transitions) and ticks them on a `Timer.periodic`. It currently couples `BuildContext`, the `Prefs` singleton, and static `TTSHelper`/`SoundHelper`, which is why it has no unit tests — refactor before testing.

### Preferences — two libraries coexist

`main.dart` initializes **both** `prefs` (`Prefs.init()`, used elsewhere as `Prefs.getX('key')`) and `pref` (`PrefServiceShared` wrapped in a `PrefService` widget, used for settings UI). When adding a preference, match whichever the surrounding code uses; do not assume one canonical API.

### Localization

Strings live in `lib/l10n/*.arb`; `lib/generated/l10n.dart` (the `S` class) is generated by `scr translations` (intl_utils). Translations are managed externally via Weblate — edit `.arb` files, not the generated `S` class.

### Theming

Material 3 with `dynamic_color` (Material You). The app reseeds from `lightDynamic`/`darkDynamic` when available, falling back to `Colors.blue`. `flutter_phoenix` is wrapped around the app so settings changes can hot-restart it.

## Lint conventions (`analysis_options.yaml`)

`require_trailing_commas` and `prefer_expression_function_bodies` are enforced — both affect formatting. `sort_pub_dependencies` is on, so keep `pubspec.yaml` alphabetized within each section.

## Commit policy

- Commit after every successful change — do not batch unrelated work.
- **Always amend** the previous commit when the new change is a continuation of it (fixup, follow-up tweak, missed file, related polish). Reserve new commits for genuinely separate changes.
- Exception: if the previous commit has already been pushed to the remote, never amend it — make a new commit instead.

## Android toolchain

Current pinned versions (in `android/`):

- AGP `8.12.2` (`settings.gradle`) — minimum 8.6.0 required by current `androidx.core` transitive deps.
- Gradle wrapper `8.14.5` (`gradle/wrapper/gradle-wrapper.properties`) — AGP 8.12 requires ≥ 8.13.
- Kotlin Gradle plugin `2.2.21` (`settings.gradle`) — 2.2.x bug-fix series; 2.2.0 was the initial 2.2 release.
- `compileSdk 36` (`app/build.gradle`) — required by `fluttertoast 9.x`.
- `org.gradle.jvmargs=-Xmx2048M`, `org.gradle.parallel=false`, `org.gradle.workers.max=1` in `gradle.properties` — host-specific tuning for a ~4 GiB build VM. Bump heap and re-enable parallel/workers on a workstation with more headroom.
- `org.gradle.daemon=true` and `android.enableJetifier=false` — daemon stays warm across runs (saves JVM cold-start); Jetifier is off because all plugins are already AndroidX. If the daemon gets memory-tight, stop it with `./gradlew --stop` from `android/`.
- Release signing falls back to debug-signing when `key.properties` is absent. `release.sh` re-signs the unsigned-by-the-build APK with `apksigner` afterward — that flow still works because `apksigner` doesn't care what signature is on the input.

### Vendored `soundpool`

`soundpool` is discontinued upstream; its only published version (2.4.1) still references the V1-embedding `PluginRegistry.Registrar` and won't compile on Flutter 3.32+. A patched copy lives in `local_plugins/soundpool/` (V1 `registerWith` companion stripped; V2 `FlutterPlugin` path untouched) and is wired in via `dependency_overrides` in `pubspec.yaml`. If you ever bump the audio plugin, you can drop both the override and the vendored directory.

## Release

Releasing is a version bump: CI (`.github/workflows/release.yml`) creates tag `vX.Y.Z` and the
GitHub release with both signed split-per-ABI APKs. **Never push tags or run
`gh release create` by hand.** Shared convention: workspace `templates/README.md`, "Releasing
(Android)". When the user says **"Create a release"**:

1. **Summarize commits** since the last tag: `git log $(git describe --tags --abbrev=0)..HEAD --oneline`.
2. **Pick the bump**: minor if any `feat:` commit is in that range, else patch (major only for
   breaking changes).
3. **Bump `version:` in `pubspec.yaml`** to `'X.Y.Z+N'`. `N` is the versionCode and must be
   greater than the last release's (CI refuses otherwise). Releases up to v2.3.0 had no `+N`,
   so Flutter built them with `N` = 1. The APK's versionCode adds a per-ABI offset
   (arm64 `2000+N`, armv7 `1000+N`), so comparing `N` is enough.
4. **Prepend a `CHANGELOG.md` entry** `# [X.Y.Z](…/releases/tag/vX.Y.Z) (date)`, grouped into
   New Features, Fixes and Under the Hood, with emojis where they add meaning. CI extracts it
   by that header as the release notes and falls back to generated notes if it's missing.
5. **Commit** `chore: release vX.Y.Z` and **push `main`**. A push that doesn't change the
   version is a no-op; `workflow_dispatch` re-runs a failed release of the current version.

CI on every push (`CI.yml`) runs analyze + test + debug build. Signing uses the
`KEYSTORE_BASE64` / `KEYSTORE_PASSWORD` repo secrets with the workspace keystore's alias
`my-key` (hardcoded); the `KEY_ALIAS` secret is unused.

### Local `release.sh` speed tips

- `./release.sh <keystore-password>` runs the full `scr build` codegen pipeline first. After `.arb`/schema/asset/`pubspec.yaml` changes, that's what you want.
- For repeat builds with no codegen-input changes, use `./release.sh --skip-codegen <keystore-password>` — saves the five Dart-VM cold starts.
- Do **not** run `flutter clean` between builds unless a plugin version changed; it wipes the 2–3 GB Kotlin/dex/R8 cache and forces a from-scratch rebuild.

`release.sh` is the local-dev equivalent and re-signs the build output with
`apksigner` from a checked-out keystore (`../my-debug.jks`); it is not used
by CI.
